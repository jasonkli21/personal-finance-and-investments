# PostgreSQL / Neon contract

Current architecture, 2026-10-03. PostgreSQL 16 locally; ordinary Neon PostgreSQL in cloud. SQLAlchemy 2 + psycopg 3 and Alembic are the single active engine and migration path. [ADR 0002](adr/0002-gcp-neon.md) records the decision.

## Connections and migrations

DATABASE_URL accepts normal postgres/postgresql/psycopg URLs, normalized to psycopg. In production, require a Neon host, credentials and `sslmode=verify-full&sslrootcert=system`; do not log connection strings. Secret Manager injects the runtime value. Configure a least-privilege application role separately from a schema-owning migration role where used. Optional MIGRATION_DATABASE_URL overrides runtime only for migrations/operator engine purpose; use a direct endpoint. Alembic's NullPool avoids persistent migration connections. Normal settings validation does not fetch secrets; Cloud Run supplies pinned versions through service identity.

Use small runtime pools, pre-ping and connect/recycle bounds. Provision application instances, worker executions and operator connections within the reviewed Neon connection envelope. Terraform defaults to two API instances, concurrency eight, pool five with zero overflow. Job executions also consume connections; parallel invocation has no global infrastructure concurrency cap, so monitor/fence triggers and retain an operator backlog drain procedure.

Run `uv run --directory services/api --locked alembic upgrade head`. Never edit an applied revision. Add a migration for any persistent change; validate fresh install and representative populated upgrade, constraints, indexes, Decimal roundtrip and backfill preservation. Alembic's widened 128-character version table is retained for descriptive revision identifiers. Runtime startup does not migrate or seed automatically.

## Transactions and finance correctness

Keep UUIDs generated by the app, NUMERIC/Decimal, immutable source revisions, scoped identifiers, provenance and FK/check/uniqueness constraints. Keep rows/bytes bounded for memory, latency, review usability and retry cost. Large imports stage unpublished batches and publish atomically. Provider/parser/filesystem/model calls finish before repeatable DB-only transactions. `run_database_unit` retries only PostgreSQL `40001` serialization failures and `40P01` deadlocks, with fresh sessions and capped attempts/backoff. Integrity errors and other failures do not retry blindly. Domain stale revisions return conflicts rather than silently rebasing.

Durable jobs use existing conditional status/owner/generation/expiry/cancellation predicates inside every staging/completion transaction. Cloud Run execution is infrastructure, not queue authority. No automatic canonical publication from extraction; results enter review.

## Required evidence

Ordinary CI uses disposable PostgreSQL 16: fresh migration, populated 0002 upgrade, source-backed finance workflows, concurrency, job fencing and encrypted recovery. Browser journeys require the disposable loopback DB gate. A local or mocked result is never real Neon/GCP evidence.

The disposable Neon suite is destructive to its dedicated test branch/schema. Require `RUN_NEON_INTEGRATION=1`, `NEON_TEST_DATABASE=disposable`, `NEON_TEST_DATABASE_URL` and direct `NEON_TEST_MIGRATION_DATABASE_URL`; never point them at production. The two endpoints must identify the same branch/database. The evidence runner requires committed source, RELEASE_IMAGE_DIGEST and a private EVIDENCE_CONFIGURATION_KEY (32+ characters) for connection HMACs. It emits hashes/counts only; missing/skipped checks block promotion.

Real tests cover fresh Alembic, populated upgrade, reconnect, bounded retry and Stage 1 golden/batched/interrupted/concurrent publication. Hosted auth, private GCS access and Neon/GCS recovery use separately reviewed evidence records. Real idle/suspend reconnect and pooled runtime resource envelope require the operations rehearsal; a disposal/reopen smoke alone cannot prove cold-start behavior.
